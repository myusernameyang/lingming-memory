## 简介

大模型聊得越久，上下文越长、越贵、越慢。**灵铭记忆**的思路：不喂完整长上下文，而是用一个本地小模型把每句对话映射到一个**稀疏 top-k 坐标**（k 个 bar = k 级地址），查询时按坐标**桶交集寻址**，直接命中最相关的历史。

核心洞察一句话：**回忆的本质是"似曾相识"（相似度），稀疏坐标就是相似度的离散化——相似输入自然落到相同地址，O(k) 直接命中，不用 O(N) 逐个比。**

## 🔍 检索流程（两条路，按查询形态分流）

```
retrieve(query)
  ├─ query 提得出标识符（英文/型号/含数字，长度>=3）
  │    → 倒排索引精确命中（ERR-7f3a9c、rebar、535 这类）
  │      句向量对随机串几乎无区分力，实测 hit@1 只有 0.600；倒排是 1.000
  └─ 提不出标识符
       → 坐标桶并集 → 桶内限流 per_bar=3 → 余弦细排
```

**两个关键设计：**

1. **桶内限流**（`per_bar`）：坐标桶并集在库变大时会几乎覆盖全库（N=2000 时候选 1539 条，退化成全表扫描）。每个桶只保留余弦前 M 条进候选，候选上限 = `k × M`，**与库大小无关**。实测 N=1000 时候选 807 → 22，hit@1 不变。

2. **标识符分流**：排障类记忆里大量是错误码、驱动版本、寄存器名。这类 token 走倒排，不走向量。两路**必须分流不能并集**（并集会让候选重新膨胀到库大小）。

## ✨ 为什么比 RAG 强

| 维度 | RAG（余弦检索） | 灵铭（坐标寻址） |
|---|---|---|
| **召回准确率**（唯一可解的合成查询） | — | **0.967** |
| **检索复杂度** | O(N·d)，随记忆量涨 | **O(d·C + k·M)**，候选数与库大小无关 |
| **单次检索耗时**（N=100 万） | 1.07 ms | **0.0098 ms** |
| **索引方式** | 稠密向量余弦 argmax | 稀疏 top-k 桶交集 + 桶内限流 |

稀疏坐标（top-k）比稠密 embedding（cos）更「判别」：相似输入 → 相同 top-k → 直接命中。

> ⚠️ 关于精度数字要看清条件：0.967 是在**合成测试集**（每条查询唯一可解）上测的。
> 早期文档里的 "100% vs 56%" 用的是另一套真实对话样本，两套不可直接对比。
> 真实使用下的准确率还缺数据——这是当前最需要补的（见「已知局限」）。

## 📊 容量曲线（N 从 60 加到 2000）

| N | hit@1 | 无限制时候选 | `per_bar=3` 后候选 |
|---|---|---|---|
| 60 | 1.000 | 56 | 5 |
| 250 | 1.000 | 233 | 6 |
| 1000 | 1.000 | 807 | 7 |
| 2000 | 1.000 | 1539 | 7 |

**命中率不随库大小掉，但候选数必须限流**——这是 `per_bar` 存在的理由。


## 安装

```bash
dsh plugin --profile desktop add github:myusernameyang/lingming-memory
```

重启 DSH，聊天框出现「灵铭记忆」开关。插件自动检测 Python 环境、自动 `pip install -r requirements.txt`、自动拉起本地服务。

## 使用

1. 聊天框输入 `/lingming` 开启；
2. 之后你跟 agent 的**每句话都会写进记忆**（存用户 + 助手，带角色标签）；
3. 下一轮自动**按坐标召回相关历史**，拼进上下文（替代长上下文）。

```
/lingming          开关
/lingming-status   看已存多少条记忆 / 多少个坐标桶
/lingming-save     保存坐标权重（coord.pt）
```

## 训练坐标

坐标投影 `W_coord` 需要先训练，让它学会「语义相似 → 相同坐标」。用「相似对」训练（对比损失，无需 API）：

```bash
# data.json：{"pairs": [["我叫小明", "我的名字是小明"], ["喜欢篮球", "爱打篮球"]]}
python train/train_coord.py train/data.json   # 产出 coord.pt
```

> 不训练也能跑（用随机坐标），但召回质量取决于坐标训练的好坏。正式用建议喂你自己的「相似对」数据。

## 接口

| 接口 | 说明 |
|---|---|
| `POST /write` | 存记忆 → 坐标 top-k 分桶 |
| `POST /retrieve` | 查询 → 坐标桶交集 → 命中最相关 |
| `POST /save` | 保存坐标权重（coord.pt） |
| `GET /status` | 状态（记忆数 / 坐标桶数） |

## 📌 已知局限

**合成测试集测不出来的东西**（目前是主要风险）：

1. **模糊提问**——"那个配置呢"这类。查询本身信息不足，实测用"相似历史 query 加权"也救不了：
   模糊查询与所有兄弟条目的具体查询余弦全在 0.75 以上，加权会把它们一起拉上来。
   **信息不足不能用回忆补。**
2. **重复提问**——用户第二次说同一件事。这是记忆失败最硬的信号，也是当前缺的基线。
3. **记重 / 记反 / 该忘没忘**——合成集里不存在。

**参数敏感性**：`per_bar=3` 在合成集上无损，但真实记录的同桶相似度更高，
可能需要 `per_bar=6` 或自适应。没有真实数据前，这个值是猜的。
